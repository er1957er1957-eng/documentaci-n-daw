# Versionado de la plataforma

## Objetivo
El sistema debe mantener un control claro de cambios funcionales y documentales para evitar regresiones entre versiones del producto.

## Estrategia
- Versionado semver: `MAJOR.MINOR.PATCH`
- Cambios funcionales relevantes se publican en una nueva versión menor.
- Correcciones críticas se entregan como parches.
- La documentación del release debe acompañar cada versión.

## Rúbrica sugerida
- `1.0.0`: lanzamiento inicial del sistema.
- `1.1.0`: nuevas métricas y permisos.
- `1.2.0`: mejoras en importación y automatización.
- `1.2.1`: correcciones de bugs de producción.

## Requisitos de gestión
- Cada release debe indicar mejoras, fixes y riesgos conocidos.
- Se deben conservar notas de cambios para soporte y auditoría.
- La compatibilidad con clientes antiguos debe documentarse cuando exista.

## Ejemplo de changelog
```md
## 1.2.0
### Añadido
- Dashboard de incidencias por equipo.
- Importación desde CSV.

### Corregido
- Error en cierre de incidencias con permisos parciales.
```

## Beneficios
El versionado permite controlar cambios, facilitar actualizaciones seguras y mejorar la trazabilidad operativa.
